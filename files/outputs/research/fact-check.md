## 三、六个讨论主题（多源综合）

### 1. 能力提升
- 【事实】按 S3 摘要，公开模型多能触发崩溃，但到达任意代码执行的少见（F5）。
- 【推论】若 F1 成立，高阶利用能力正从封闭前沿模型扩散到开放权重模型；但 F1 为单一厂商自测，且与 S3 能力阶梯的对应未核实。
- 【待核实】F1 与 S3 公开结果的实验配置是否一致。

### 2. 可获得性
- 【事实】权重可公开下载并本地部署（F6），另有托管 API 与编码套餐（F7）；在野已出现把开放权重模型部署在被入侵基础设施上以规避监控的做法（F12，非 GLM 专属）。
- 【推论】权重一旦公开，厂商侧拒绝策略、API 监控与封号对本地副本不再起作用；F10 的机制与 F2 方向一致。
- 【待核实】S4 许可条款是否限制有害用途，以及能否执行。

### 3. 补丁窗口
- 【事实】剔除异常值后，2023 年在野利用平均 TTE 已降至数天，零日占比上升（F8、F9）。
- 【推论】若低成本模型能缩短从公开修复到可用利用的时间，补丁窗口将进一步受压；F3 仅为单例迹象，不能证明窗口已经缩短。

### 4. 开放权重的利弊
- 【事实】开放权重便于自托管与独立评估（F6）；白盒条件下拒绝行为可被移除（F10）。
- 【推论】利：研究者与防守方可离线使用、独立审计；弊：安全对齐难以在下游保持。利弊并存，不宜单向定论。
- 【争议】S1 发布方是竞争厂商，强调开放权重风险可能带有立场；S4/S5 的厂商说法同样未经独立验证。

### 5. 评测局限
- 【事实】S3、S9 本次只读摘要；S1 数字限定见 F1–F3。
- 【推论】阶梯得分（F5）、端到端占比（F1）、模拟响应率（F2）与真实攻击结果是不同的量，不得相互换算。
- 【待核实】S2 访问失败，目前缺少可核验的政府独立评测。

### 6. 防守启示
- 【事实】S6"影响"一节建议加快打补丁、分段架构与访问控制，并提醒不要只凭公开利用代码或媒体热度排序。
- 【厂商说法】S10"Google 如何防范 AI 滥用"一节描述 Google 自身的模型层防护与主动红队测试，属平台方措施而非对一般组织的建议；S10 供应链一节只描述风险。
- 【厂商说法】S1 第三节的观点与其商业利益相关，宜与 S6 对照使用。
- 【推论】TTE 压缩（F8/F9）叠加开放模型能力扩散（F12 所示部署方式），缩短修复周期与纵深防御比依赖模型侧拒绝更可靠。
